## 1. ブランド・プロダクトコンセプト

### 1-1. Are-Attakke（あったっけ）ブランド

**Are-Attakke（略称: AA）** は、消耗品の在庫を「ある？なかった？」と素早く確認するための **シリーズブランド** である。ブランド名は日常の「あれ、あったっけ？」という問いかけに由来し、店頭や作業現場で「持っているか分からない」消耗品の **重複購入・欠品** を防ぐことを目的とする。

| 項目 | 内容 |
|---|---|
| ブランド名 | Are-Attakke（あったっけ） |
| 略称 | **AA** |
| ジャンル | 消耗品管理アプリ |
| 提供価値 | 「あれ、あったっけ？」を解消し、無駄な出費と準備不足を防ぐ |

### 1-2. シリーズ展開方針

本プロダクトは Are-Attakke シリーズの **第一弾** として位置づける。共通のブランド基盤（AA マーク・UI パターン・在庫管理コア）の上に、領域ごとのアプリを横展開する。

| 順序 | シリーズ（案） | アイコン中央文字 | 対象消耗品の例 | 状態 |
|---|---|---|---|---|
| **第1弾** | AA × **釣** | **釣** | フック、シンカー、ルアー、仕掛け小物 | **本アプリ（開発中）** |
| 第2弾 | AA × 手芸 | 手芸（1文字または略字） | 糸、ビーズ、生地、副資材 | 構想 |
| 第3弾 | AA × 工務 | 工 | ネジ、ビス、シーリング、建築資材 | 構想 |
| 第4弾 | AA × プラモ | 模 | ランナー、パテ、サンドペーパー、塗料 | 構想 |

各シリーズは同一ブランドの派生アプリとして、以下を共通化する。

- **AA ロゴマーク**: 2 つの「A」の骨格を円弧状に変形した向かい合うモチーフ
- **領域文字**: シリーズごとに中央へ領域を表す 1 文字を配置（本アプリは **「釣」**）
- **UI パターン**: ノンキーボード数量変更・買い物リスト・AI 写真登録などの操作体系
- **在庫管理コア**: カテゴリ分類・数量管理・オフライン対応のデータモデル

### 1-3. アプリアイコン設計（第1弾: 釣）

第1弾アプリのアイコンは、シリーズ共通の AA マークと領域文字「釣」を組み合わせて構成する。

| 要素 | 仕様 |
|---|---|
| AA マーク | 2 つの「A」のストロークを円弧状に変形し、天地対称に向き合わせて円を形成 |
| 中央文字 | **釣**（本シリーズの領域識別子） |
| 背景色 | ダークネイビー（`#080e1d` 〜 `#0d1f3c` のグラデーション） |

### 1-4. 本アプリの位置づけ

本要件定義書が対象とする **My Fishing Gear（釣具在庫管理アプリ）** は、Are-Attakke シリーズ第1弾であり、**釣り消耗品** の在庫管理に特化した PWA である。アプリ名は当面「My Fishing Gear」を維持しつつ、ブランディング・アイコン・将来の横展開設計は Are-Attakke シリーズ基準に沿って進める。

## 2. システム概要

本システムは、釣り人が所有する仕掛け、ルアー、小物（フック、シンカー等）の在庫をスマートフォン上で効率的に管理するための **Progressive Web Application (PWA)** である。

手動入力の手間を極限まで減らす「AI写真解析登録」と、店頭や現場での素早い操作を可能にする「ノンキーボードUI」を特徴とし、釣具の重複購入（無駄な出費）を防止することを目的とする。これは Are-Attakke ブランドが掲げる「あったっけ問題」の解消というコンセプトを、釣り領域において具体化したものである。

### 技術スタック概要

| 項目 | 技術・サービス |
|---|---|
| フロントエンド | Next.js 16 (App Router) + React 19 + TypeScript |
| スタイリング | Tailwind CSS v4 |
| PWA | @ducanh2912/next-pwa（Service Worker + Web Manifest） |
| 在庫データ永続化 | 未ログイン: localStorage / ログイン: Supabase（items・Storage） |
| 認証 | Supabase Auth（Magic Link / Google OAuth） |
| 課金 | Stripe（サブスクリプション） |
| AI解析 | Google Gemini API（gemini-2.5-flash-lite） |
| デプロイ | Vercel |

## 3. 対象ユーザーと利用シーン

- **ターゲットユーザー**: 手持ちの釣具（特に仕掛けの号数やルアーのカラー）を把握しきれず、釣具店で同じものを重複購入してしまう傾向がある釣り人。
- **利用シーン**:
  - **自宅**: 購入した釣具をまとめて登録・整理する、釣行前に在庫を確認して準備する。
  - **釣具店の店頭**: 電波が不安定な場合もある店内で、買い足すべきアイテム（在庫切れ）を片手で素早く確認する。
  - **釣り場（船上・堤防など）**: オフライン環境下で、仕掛けを消費した際にその場で在庫数を減らす。

## 4. 機能要件

### ① AI画像解析・登録モジュール

- **F-1-1: カメラ撮影および画像選択**: ブラウザのカメラAPIを使用して釣具（パッケージまたは本体）を撮影、もしくは端末のアルバムから画像を選択できること。
- **F-1-2: AIマルチモーダル解析**: 撮影された画像を Google Gemini API に送信し、`[メーカー名、製品名、大カテゴリ、中カテゴリ、サイズ（号数/ウエイト）、カラー]` を自動で判別・抽出すること。画像は base64 エンコードして `/api/analyze` エンドポイント経由でサーバーに送信する。
- **F-1-3: 解析結果確認・修正**: AIの解析結果をフォームに自動入力し、万が一誤りがある場合のみ限定的に手動修正できること。
- **F-1-4: 重複チェック（名寄せ）**: すでに同じ製品（同一メーカー・名・スペック）が登録されている場合は、既存の在庫に「+1」するか確認すること。
- **F-1-5: 手動登録**: 写真を使わず、メーカー・製品名・カテゴリ・数量・スペック（カラー/号数/重量）をフォーム入力して商品を登録できること。AI解析は不要（オフライン可）。
- **F-1-6: AI解析フォールバック**: `GEMINI_API_KEY` 未設定時またはAPI呼び出し失敗時、モック解析結果を返してアプリが停止しないこと。

### ② 在庫一覧・カテゴリ管理モジュール

- **F-2-1: カテゴリ絞り込み・検索**: 「大カテゴリ（LURE/RIG/HOOK/LINE/OTHER）」＞「中カテゴリ」の階層で、タップ操作のみで素早く絞り込めること。
- **F-2-2: 在庫ステータス表示（カード型UI）**: 各釣具をカード形式で表示し、現在の数量を表示。在庫数が「0」のアイテムは視覚的に「要補充（在庫切れ）」であることを強調すること。
- **F-2-3: 商品情報編集**: 登録済み商品のメーカー・製品名・カテゴリ・数量・スペックを後から修正・保存できること。
- **F-2-4: 商品削除**: 登録済み商品を編集画面から削除できること。削除前に確認ダイアログを表示し、関連スペックデータも合わせて削除すること。

### ③ ノンキーボード数量変更モジュール（最重要UI）

- **F-3-1: タップによるカウントアップ**: アイテムカード（または専用エリア）をシングルタップ（短押し）することで、在庫数を即座に「+1」すること。
- **F-3-2: 長押しによるカウントダウン**: アイテムカードを長押し（ロングプレス）することで、在庫数を即座に「-1」すること。タップ・長押し時に触覚フィードバック（Android: `navigator.vibrate()`、iOS: クリック音＋視覚フィードバック）を提供すること。
- **F-3-4: 楽観的 UI 更新**: 数量変更は画面を即時更新し、バックグラウンドでサーバー API に同期すること（連続タップはデバウンスでまとめて送信）。
- **F-3-3: 数量変更時のキーボード非表示**: 数量の変更（+1 / -1）においては、数値入力用のソフトキーボードを一切ポップアップさせないこと。

### ④ 買い物リスト（店頭確認）モジュール

- **F-4-1: 自動補充リスト化**: 在庫数が「0」になったアイテム、またはユーザーが個別に「補充フラグ（`is_shopping_list`）」を立てたアイテムを、自動的に「買い物リスト」タブに集約すること。
- **F-4-2: 店頭閲覧モード**: 釣具店の棚の前で、補充すべきアイテム（製品名・サイズ・カラー・パッケージ画像）だけを縦スクロールで一気に確認できる専用ビューを提供すること。

### ⑤ 認証モジュール

- **F-5-1: Magic Link 認証**: メールアドレスにワンタイムリンクを送信し、パスワードなしでログインできること（Supabase OTP）。
- **F-5-2: Google OAuth**: Google アカウントを使用した OAuth ログインをサポートすること。
- **F-5-3: セッション管理**: `Next.js Middleware` でリクエストごとに Supabase セッションを更新し、認証状態を維持すること。
- **F-5-4: 認証コールバック**: `/auth/callback` ルートで OAuth コードおよび Magic Link のトークン交換を処理すること。

### ⑥ ライセンス・マネタイズ管理モジュール（Stripe）

- **F-6-1: 無料版の制限（リミッター）**:
  - 登録アイテム数が **25個** に達した場合、新規登録を制限し、プレミアムプランへの課金誘導を表示すること。
  - AI画像解析の利用回数を **累計10回** までに制限すること（月次リセットなし。使い切ったらプレミアムへ誘導）。
- **F-6-6: クラウド保存**: ログイン時は在庫データを Supabase PostgreSQL に、写真を Supabase Storage に保存すること。初回ログイン時に localStorage のデータを自動移行すること。
- **F-6-7: バージョン表示**: アプリバージョンとビルド ID を画面右下バッジ・サイドバー・マイページに常時表示すること。
- **F-6-2: Stripe Checkout**: Stripe の Checkout Session を作成し、サブスクリプション購入フローをサポートすること（`/api/checkout` エンドポイント）。
- **F-6-3: Stripe Customer Portal**: ユーザーが自身のサブスクリプションを管理（プラン変更・解約）できるポータルを提供すること（`/api/portal` エンドポイント）。
- **F-6-4: Stripe Webhook**: `checkout.session.completed`、`customer.subscription.updated`、`customer.subscription.deleted` イベントを受信し、Supabase の `profiles.subscription_status` を更新すること。
- **F-6-5: プレミアム判定**: `profiles.subscription_status === "active"` を根拠とし、API レスポンスでプレミアム状態を返すこと。

## 5. 非機能要件

- **片手操作性**: 主要な操作ボタンを画面下部に配置するなど、片手の親指だけで「検索」「確認」「数量変更」の8割以上の操作が完結するレイアウトにすること。
- **高速起動**: アプリのアイコン（PWA ホーム画面）をタップしてから、在庫一覧または買い物リストが表示されるまでの時間を「3秒以内」とすること（Service Worker キャッシュ活用）。
- **ローカルファースト（オフライン動作）**:
  - インターネットが繋がらない、または電波が極めて微弱な環境でも、すでに登録されている在庫データの閲覧、および「タップ・長押しによる数量変更」が完全に動作すること。
  - 未ログイン時はオフライン中の数量変更を localStorage に即時保存すること。ログイン時はオンラインで Supabase API 経由で同期すること（AI画像解析はオンライン必須）。
  - Service Worker（Workbox）により静的アセットをキャッシュし、オフライン閲覧を可能にすること。
- **クロスプラットフォーム**: iOS Safari / Android Chrome / デスクトップブラウザで動作すること。PWA としてホーム画面への追加（スタンドアロンモード）をサポートすること。
- **セキュリティ**:
  - サーバー秘密鍵（`STRIPE_SECRET_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `GEMINI_API_KEY`）はクライアントに露出させないこと。
  - Stripe Webhook は署名検証（`STRIPE_WEBHOOK_SECRET`）を行うこと。
  - Supabase の RLS（Row Level Security）により、ユーザーは自分の profile・在庫データのみアクセスできること。
